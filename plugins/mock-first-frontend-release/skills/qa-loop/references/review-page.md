# Owner review page and chat-ready questions

Two temporary files for the owner's review meeting. Plain language: the reader is the product owner, not an engineer.

## Review page (HTML)

- One self-contained `.html` file: inline CSS, no external scripts or fonts, screenshots embedded as `data:` URIs after masking personal data in them (emails, phone numbers, codes): draw a solid box over it in a copy, never embed the original. Colours as CSS variables with a `prefers-color-scheme: dark` override and an explicit body background. Readable at phone width (no horizontal scroll).
- First lines: an HTML comment with Purpose / Use / Delete-when ("the testers' answers are in the register and the owner has reviewed it"); regenerate it when answers change the register.
- Saved in a local, untracked folder (never in a product repo, never published). It holds testers' screenshots, which may show personal data.
- Generated by a small script from the register, the questions doc and the extraction tables, so it can be regenerated after the testers answer. Keep the script with the scratch files, not in the project.

Sections, in this order:

1. **At a glance**: cases in the plan, passed by every tester / by some, issue rows, then one tile per verdict in plain words (VALID = we fix, INVALID = not a bug, CONFIG = setup, ASK = question, DECIDE = decision; duplicates are merged into the row they duplicate); the top 5 issues in one line each.
2. **What worked well**: every case with no issue row and no Fail mark, grouped by area; mark "passed by some, others skipped" differently from "passed by every tester". One line of highlights the testers praised.
3. **Issues by area**: one card per register row: id, case, tester(s), verdict badge, the verbatim quote, a one-line "what we'll do" in plain words, and the screenshot inline if the row has one.
4. **Decisions needed**: product requests plus any item whose fix waits on the owner (rules, wording, naming), one line each.
5. **Questions going back to the testers**: the same content as the questions doc, and where the chat-ready file is.
6. **Test-plan fixes**: what the next plan changes, including blank header fields (name, device, OS, build id).

Check it in a browser before handing it over: card count equals register rows, screenshots render, both themes readable.

## Chat-ready questions (plain text)

- Short greeting and thanks; then a block for everyone, then one block per tester headed with an `@name` placeholder; numbered lines, one question each, with the case id in brackets.
- No markdown tables, no `#` headings, no internal ids except case ids testers know.
- End with "things we already have answers for (no reply needed)" as bullets, and a thank-you.
- Save it next to the review page and paste it into your reply so the owner can copy it straight away.
